## ⚠️ Two live auth bugs found & fixed 2026-09-27, both worth understanding

Found while debugging "login isn't working" by firing real requests at the running API (`curl`/direct `auth.api` calls) instead of trusting code review alone — both were silent, no error at the code level, only at runtime against real data.

1. **`src/lib/auth.ts` had regressed** — an earlier fix (role default `"user"` → `"viewer"`, removing a dead `hooks.before` block, wiring `sendResetPassword`/`sendVerificationEmail` through the email service) was **reverted by a concurrent edit** that also added legitimate new config (`trustedOrigins`, `advanced.defaultCookieAttributes`) — someone edited this file from an older base, undoing the fixes as a side effect. Re-merged: kept the new additions, restored the fixes. **If you find `defaultValue: "user"` in this file again, it's not a stray — it will break every sign-up with `FAILED_TO_CREATE_USER`.**
2. **The `admin()` plugin has its own `defaultRole` option that silently overrides `additionalFields.role.defaultValue`.** This is the one that actually matters — `admin()` registers a `databaseHooks.user.create.before` hook (see `better-auth/dist/shared/*.mjs`) that sets `role: options?.defaultRole ?? "user"` on every new user, independent of the `additionalFields` config. Fixed by passing `admin({ defaultRole: "viewer" })` explicitly. **Setting `additionalFields.role.defaultValue` alone is not enough while the admin plugin is active** — don't "fix" this again by only touching that field.
3. **`prisma/seed.ts` set `Account.accountId` to the user's *email*; better-auth's sign-in flow looks up the credential account by `accountId === userId`** (`node_modules/better-auth/dist/api/routes/sign-in.mjs`: `.find(a => a.providerId === "credential" && a.accountId === user.id)`). With the wrong `accountId`, the lookup silently fails before password verification even runs — `verifyPassword()` against the stored hash returned `true` when tested directly, so the hash itself was always fine; the account was just never found. Fixed in both the super-admin and reviewer account blocks (create *and* update paths — the update path previously left a stale `accountId` in place even after reseeding). **If you ever hand-create an Account row instead of going through `auth.api.signUpEmail`, `accountId` must be the user's `id`, not their email.**

**Diagnostic pattern that found this** (worth reusing, not just for this bug): don't trust "should work" from code review — fire the actual endpoint (`curl -X POST http://localhost:<port>/api/auth/sign-in/email ...`), and when the error message is generic, call `auth.api.signUpEmail`/`auth.api.signInEmail` directly from a throwaway script inside the backend directory (needs to be inside `mydubai-broker-backend/`, not `/tmp`, for relative imports to resolve) to get the real underlying error instead of the sanitized HTTP response.

## Login felt slow/unresponsive — fixed 2026-09-27 (two separate causes)

1. **Scrypt cost was double the standard preset.** better-auth's default node password hasher (`@better-auth/utils/dist/password.node.mjs`) uses `N=16384, r=16, p=1` — `r=16` is 2x the common "interactive" preset (`r=8`), costing ~2x the memory (~64MB/hash) and CPU time per login, and Node's `crypto.scrypt` runs on the small default libuv threadpool (4 threads), so concurrent logins queue up and compound the delay. Fixed via a custom hasher — new `src/lib/password.ts` (same `${salt}:${keyHex}` envelope format, just `r=8`), wired in via `auth.ts`'s `emailAndPassword.password.{hash,verify}` override, and `prisma/seed.ts` updated to import the same function instead of `better-auth/crypto`. **Existing password hashes were created at `r=16` and will NOT verify against the new `r=8` verify function — you must re-seed** (`prisma db seed`) for the super-admin/reviewer accounts to log in again; any other existing users would need a password reset.
2. **Double full-page spinner after login.** `signIn.email` triggers better-auth's client to invalidate and refetch its shared session atom (by design, via `$sessionSignal` — see `better-auth/dist/client/config.mjs`), but the login pages navigated (`router.push`) *before* that refetch resolved, so `AuthGuard` mounted on the destination page still `isPending`, re-fetched the session itself, and showed a second, separate full-page spinner right after the login button's own "SIGNING IN..." state. Fixed by having `FrontendAuthService.login` (`src/services/auth.service.ts`) `await authClient.getSession()` once before returning — warms the same shared session atom `useSession`/`AuthGuard` read from, so by the time either login page navigates, `AuthGuard` finds a non-pending cached session immediately.

Also: `src/middleware/rateLimit.ts` currently has `RATE_LIMIT_ENABLED = false` (a one-line flag, not per-callsite) — **temporarily disabled for local testing, flip it back to `true` before anything resembling production/shared use.**

- **No tests at all** — no `*.test.ts`/`*.spec.ts` anywhere, no test script beyond stubs.
- **No structured logging** — `pino` is a dependency but is never imported anywhere in `src`; all error handling is `console.error`/`console.log`.
- **No API documentation** — no OpenAPI/Swagger.
- ~~No rate limiting on auth/account-creation endpoints~~ — **FIXED** 2026-09-27. `src/middleware/rateLimit.ts` (still in-memory/per-instance, not distributed — fine for one Node process, would need a Redis-backed limiter behind multiple instances) is now applied to: the whole custom `auth.routes.ts` router (register/login/company-register/agent-register, 20/15min/IP), the better-auth catch-all mount in `routes.ts` (its own login/signup/session routes, 20/15min/IP), `POST /companies/onboarding` (10/hr/IP), and `POST /invitations/token/:token/accept` (10/hr/IP) — every unauthenticated endpoint that creates an account or logs in now has a limiter. Non-account-creation routes still have none — fine for now, revisit if abuse is observed.
- ~~No `helmet`~~ — **FIXED** 2026-09-27. `app.ts` now applies `helmet()` with its defaults (standard security headers: CSP, X-Frame-Options, etc.) before anything else. Since this is a pure JSON API (media is served directly from R2, not through this app), the defaults needed no tuning.
- ~~`JWT_SECRET` hardcoded fallback~~ — **REMOVED**, not fixed-in-place, 2026-09-27. The legacy `authenticate`/`authorize` functions in `auth.middleware.ts` (and the `jsonwebtoken` dependency, `@types/jsonwebtoken`, the `AuthRequest` type) were confirmed unused anywhere in the codebase (grepped, zero hits) and deleted outright rather than parameterizing the secret — dead code with a hardcoded secret is worse than no code. `requireAuth` (better-auth session-based, the one actually used everywhere) is untouched. Also deleted while in there: `src/middleware/errorHandler.ts`, a fully unused duplicate of `error.middleware.ts` whose dead code path passed `err.stack` directly into a response body — same "unused and worse than the thing actually in use" pattern, same fix.
- **No MFA** for sensitive roles (admin/reviewer) — zero 2FA code anywhere. Not attempted — this is a real feature (TOTP enrollment flow, recovery codes, UI), not a quick hardening fix.
- **AuditLog coverage improved but still partial.** Originally written in only 2 places (`admin.service.ts` company-status changes, `listings.service.ts` approval/archive); this pass added it to invitation send/revoke/accept, user deactivation/reactivation, and permission-override updates (`invitations.service.ts`, `companies.service.ts`). Still not written on: document review (doesn't exist yet, see Onboarding), login events, listing edits (as opposed to approval decisions), or lead actions. `admin.view_audit_log` capability still exists with no route to actually view the log — the data is being captured now in more places, but there's still no way to read it back through the API.
- **No background job infrastructure — explicitly deferred, not just missing.** The only scheduled code in the whole codebase is one hand-rolled `setInterval` (`uploads.service.ts` `startUploadCleanupJob`, purges abandoned uploads every 15 min). No cron/bullmq/agenda/etc. **Decision: skip building a real job runner for now** — this means quality scores, rank snapshots, daily rollups, document/listing expiry, and lead SLA escalation stay unimplemented even if their surrounding features get built, since all of them need something to run on a schedule. Don't reach for a job scheduler as a side effect of picking up one of those items; treat "add a job runner" as its own explicit, separately-scoped task the user hasn't asked for yet. If a feature absolutely needs scheduled execution before this is picked up, the honest move is to say so and ask, not to quietly bolt on a one-off `setInterval` like the upload-cleanup job did.
- **No malware scanning** on uploads — only size/content-type checks.
- ~~`.env.example` documents `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` that aren't in the validated schema~~ — **FIXED** 2026-09-28. Dropped both from `.env.example` (Google OAuth is fully commented out in `auth.ts`/`auth-client.ts`, nothing reads them), replaced with a one-line comment explaining why they're gone and where to re-add them if OAuth is ever wired up. `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL` were also flagged here originally but are **not actually a gap** — better-auth reads those directly from `process.env` itself (its own convention), so them not appearing in `src/lib/env.ts`'s zod schema is expected, not an oversight; left them in the example file as-is.

Frontend:
- **No tests at all**.
- ~~No password reset flow~~ — **FIXED** 2026-09-27, see "Auth/login/signup — cleaned up" at the top of this file.
- No session management UI (active sessions / revoke).
- Admin/dashboard screens hardcode English strings directly instead of pulling from the (otherwise well-wired) i18n dictionaries — i18n itself is in good shape (`src/i18n`, RTL support, 25 dictionary files per locale), just not applied everywhere.
- `DataTable.tsx` has no column sorting, no pagination, no row-selection/bulk actions — needed once admin queues and listing management tables grow past a handful of rows.

## What's already solid (don't rebuild, extend)

- Prisma schema overall — comprehensive and well thought through; the gap everywhere is service/UI code catching up to what the schema already models.
